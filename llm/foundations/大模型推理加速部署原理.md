# 大模型推理加速部署原理

大模型训练完成后，真正上线使用时进入推理阶段。推理部署关注的问题和训练不同：

```text
训练关注:
  loss 是否下降
  参数如何更新
  数据如何提升模型能力

推理关注:
  首 token 延迟
  每秒输出 token 数
  并发请求数量
  显存占用
  部署成本
  模型格式和硬件适配
```

常见推理部署工具包括：

| 工具 | 主要定位 |
|---|---|
| vLLM | 高吞吐服务端推理框架 |
| llama.cpp | 本地 CPU/GPU 轻量推理框架 |
| Ollama | 面向本地模型管理和启动的封装工具 |
| TensorRT-LLM | NVIDIA GPU 上的高性能推理框架 |
| Hugging Face TGI | 面向生产服务的推理服务框架 |

本文重点解释 vLLM、llama.cpp 和 Ollama 的原理。

## 一、大模型推理为什么慢

Decoder-only 大模型生成文本时是自回归的：

```text
prompt
  -> 生成 token1
  -> token1 拼回上下文
  -> 生成 token2
  -> token2 拼回上下文
  -> ...
```

下一个 token 依赖前面已经生成的 token，所以 decode 阶段天然是串行的。

推理慢主要来自几个方面：

| 原因 | 说明 |
|---|---|
| 模型参数大 | 每生成一个 token 都要经过所有层 |
| KV Cache 大 | 上下文越长，缓存越占显存 |
| Attention 复杂 | prompt 越长，prefill 阶段越重 |
| 显存带宽瓶颈 | decode 阶段经常受权重读取速度限制 |
| 请求长度不同 | 多用户并发时调度复杂 |
| Python 开销 | 逐 token 调用如果调度不好会浪费时间 |

所以推理加速不是单一技术，而是一组工程优化。

## 二、推理阶段的两个核心阶段

### 1. Prefill

Prefill 处理完整 prompt。

```text
用户输入 prompt
  -> 一次性送入模型
  -> 计算所有 prompt token 的 K/V
  -> 建立 KV Cache
  -> 输出第一个待采样 logits
```

特点：

- 可以并行处理多个 prompt token；
- 计算量和 prompt 长度强相关；
- 长 prompt 的首 token 延迟高。

### 2. Decode

Decode 是逐 token 生成。

```text
当前 token
  -> 读取历史 KV Cache
  -> 计算下一个 token
  -> 追加新 KV
  -> 重复
```

特点：

- 串行；
- 对延迟敏感；
- 受显存带宽、KV Cache、batch 调度影响明显。

推理框架的优化重点通常是：

```text
让 prefill 更快
让 decode 更高吞吐
让 KV Cache 更省显存
让多请求调度更高效
```

## 三、KV Cache 是推理加速的基础

Transformer Attention 中，每个 token 都会产生 Key 和 Value。

如果没有 KV Cache，生成第 n 个 token 时，需要重新计算前面所有 token 的 K/V：

```text
每一步都重新处理完整上下文
```

这样非常慢。

有了 KV Cache：

```text
历史 token 的 K/V 保存起来
每次只计算新 token 的 K/V
当前 Query 直接和历史 Key 做 attention
```

KV Cache 的代价是显存。

它的大小大致和下面因素成正比：

```text
batch_size
context_length
num_layers
num_kv_heads
head_dim
dtype_size
```

所以部署时经常会遇到：

```text
模型权重能放下
但并发一高或上下文一长，KV Cache 放不下
```

这也是 vLLM 的 PagedAttention 要解决的问题。

## 四、vLLM 的原理

vLLM 是一个面向高吞吐服务端部署的大模型推理框架。它的核心目标是：

```text
在有限 GPU 显存下，尽可能提高并发和 token 吞吐
```

vLLM 最重要的设计是：

- PagedAttention；
- continuous batching；
- 高效 KV Cache 管理；
- OpenAI-compatible API server；
- prefix caching 等服务端优化。

### 1. vLLM 解决的核心问题

多用户同时请求时，每个请求的 prompt 长度和生成长度都不同：

```text
请求 A: prompt 200 token, 生成 50 token
请求 B: prompt 2000 token, 生成 500 token
请求 C: prompt 30 token, 生成 20 token
```

传统做法如果使用固定 batch，很容易出现：

- padding 浪费；
- 短请求等长请求；
- KV Cache 显存碎片；
- 显存预分配过大；
- 并发上不去。

vLLM 的核心就是让这些请求更高效地共享 GPU。

### 2. PagedAttention

PagedAttention 是 vLLM 的关键机制。

普通 KV Cache 常按连续内存分配：

```text
Request A: 连续一大段 KV Cache
Request B: 连续一大段 KV Cache
```

问题是每个请求生成长度不确定。如果预留太多，浪费显存；预留太少，又要频繁搬移或重新分配。

PagedAttention 借鉴操作系统分页思想，把 KV Cache 切成固定大小的 block：

```text
KV Cache Block 0
KV Cache Block 1
KV Cache Block 2
KV Cache Block 3
...
```

每个请求只拿自己需要的 block：

```text
Request A -> block 1, block 7, block 9
Request B -> block 2, block 3
Request C -> block 4
```

这样做的好处：

| 优点 | 说明 |
|---|---|
| 减少显存浪费 | 不必为每个请求预留最大长度 |
| 降低碎片 | 以 block 为单位管理 KV |
| 支持动态增长 | 请求生成更多 token 时再分配 block |
| 更适合并发 | 大量不同长度请求可以混合调度 |

可以类比操作系统虚拟内存：

```text
逻辑上的连续上下文
  -> 映射到物理上不连续的 KV block
```

Attention 计算时，vLLM 通过 block table 找到当前请求对应的 KV block。

### 3. Continuous Batching

传统 batch 可能是：

```text
等一批请求凑齐
  -> 一起开始
  -> 一起结束
```

如果其中一个请求很长，其他短请求可能被拖慢。

continuous batching 是连续批处理：

```text
每个 decode step 都可以动态加入新请求、移除完成请求
```

例如：

```text
step 1: A, B, C 一起生成
step 2: C 完成，D 加入
step 3: A 完成，E 加入
```

这样 GPU 可以一直保持较高利用率。

### 4. vLLM 的推理流程

可以简化理解为：

```text
请求进入队列
  -> scheduler 判断哪些请求进入 batch
  -> prefill prompt，建立 KV block
  -> decode 阶段连续批处理
  -> 每步生成 token
  -> 请求结束后释放 KV block
```

### 5. vLLM 适合什么场景

适合：

- 多用户并发；
- API 服务；
- GPU 服务端部署；
- 长上下文或请求长度差异大的场景；
- 追求高吞吐。

不太适合：

- 只想本地简单跑一个模型；
- 纯 CPU 推理；
- 非 NVIDIA/不支持的硬件环境；
- 只需要极简桌面使用。

## 五、llama.cpp 的原理

llama.cpp 是一个轻量级大模型推理项目，最初目标是在普通电脑上运行 LLaMA 模型。它的核心特点是：

```text
用 C/C++ 实现，尽量减少依赖，通过量化和底层优化让模型能在本地 CPU/GPU 上运行。
```

### 1. llama.cpp 解决的核心问题

很多人没有高端 GPU，但希望在本地运行大模型。

llama.cpp 关注：

- 低依赖；
- 跨平台；
- CPU 可运行；
- 支持 Apple Silicon、CUDA、Metal、Vulkan 等后端；
- 支持低比特量化；
- 使用 GGUF 模型格式。

### 2. GGUF 模型格式

GGUF 是 llama.cpp 常用的模型文件格式。

它通常包含：

- 模型权重；
- 模型结构元信息；
- tokenizer 信息；
- 量化类型；
- RoPE、context length 等配置。

一个 `.gguf` 文件可以被 llama.cpp 直接加载。

```text
model.gguf
  -> weights
  -> tokenizer metadata
  -> architecture metadata
  -> quantization metadata
```

这比一堆分散的配置文件更适合本地分发和加载。

### 3. 量化是 llama.cpp 的核心

大模型参数很多，如果用 FP16 存储：

```text
7B 参数 * 2 bytes ≈ 14GB
```

如果量化到 4bit，理论权重体积会大幅下降。

llama.cpp 支持很多量化格式，例如：

```text
Q4_0
Q4_K_M
Q5_K_M
Q8_0
```

量化的目标：

```text
用更低精度保存权重
  -> 降低内存/显存占用
  -> 提高本地可运行性
```

不同量化级别的取舍：

| 类型 | 特点 |
|---|---|
| Q8 | 精度损失小，体积较大 |
| Q5 | 精度和体积折中 |
| Q4 | 体积小，常见本地部署选择 |
| Q2/Q3 | 更省内存，但质量损失更明显 |

### 4. CPU/GPU 混合推理

llama.cpp 可以把部分层放到 GPU，剩余放到 CPU。

常见参数类似：

```text
--n-gpu-layers 35
```

含义是把多少层 offload 到 GPU。

如果显存不足，可以减少 GPU 层数；如果显存充足，可以尽量把更多层放到 GPU。

### 5. llama.cpp 的推理优化

llama.cpp 的加速来自多方面：

| 优化 | 说明 |
|---|---|
| C/C++ 实现 | 减少 Python 框架开销 |
| 量化矩阵乘 | 低比特权重降低内存带宽压力 |
| 多线程 CPU | 利用本机 CPU 核心 |
| Metal/CUDA/Vulkan | 利用不同 GPU 后端 |
| KV Cache | 自回归生成复用历史 K/V |
| mmap | 通过内存映射加载模型，减少启动开销 |
| GGUF | 简化模型元信息和权重加载 |

### 6. llama.cpp 适合什么场景

适合：

- 本地运行模型；
- 无 GPU 或小显存设备；
- Mac、Linux、Windows 桌面；
- 边缘设备；
- 离线推理；
- 对部署依赖要求很低的场景。

不太适合：

- 大规模高并发服务；
- 极致 GPU 吞吐场景；
- 需要复杂服务端调度的场景。

## 六、Ollama 的原理

Ollama 可以理解为一个本地大模型管理和运行工具。它并不是单纯的底层推理内核，而是把模型下载、模型管理、运行服务、API 调用、Modelfile 配置等包装起来。

简单说：

```text
Ollama = 本地模型管理工具 + 推理服务封装 + 模型配置封装
```

它底层很多模型运行能力依赖 llama.cpp 生态和 GGUF 模型格式。

### 1. Ollama 解决的核心问题

直接使用 llama.cpp 时，你可能需要关心：

- 下载哪个 GGUF 文件；
- 用什么量化版本；
- 怎么写启动参数；
- tokenizer 和模板怎么配；
- prompt template 怎么写；
- 怎么提供 HTTP API；
- 多个模型怎么管理。

Ollama 把这些包装成更简单的命令：

```bash
ollama run llama3
ollama run qwen2.5
ollama serve
```

### 2. Modelfile

Ollama 使用 `Modelfile` 描述模型配置。

一个简单例子：

```text
FROM llama3

PARAMETER temperature 0.7
PARAMETER top_p 0.9

SYSTEM """
你是一个严谨的中文助手。
"""
```

Modelfile 可以配置：

- 基础模型；
- system prompt；
- temperature；
- top_p；
- stop words；
- adapter；
- prompt template。

### 3. Ollama 的运行方式

Ollama 通常会启动一个本地服务：

```text
用户请求
  -> Ollama API
  -> 加载模型
  -> 调用底层推理引擎
  -> 流式返回 token
```

它对用户隐藏了很多底层细节。

典型交互：

```bash
ollama run qwen2.5
```

或者通过 HTTP API 调用：

```text
POST /api/generate
POST /api/chat
```

### 4. Ollama 和 llama.cpp 的关系

可以这样理解：

```text
llama.cpp:
  更底层
  关注模型如何高效跑起来
  关注 GGUF、量化、CPU/GPU 后端

Ollama:
  更上层
  关注模型如何下载、管理、配置、调用
  提供更简单的本地使用体验
```

如果你想深入控制推理参数、编译选项和底层后端，直接用 llama.cpp 更灵活。

如果你想快速在本地跑模型并提供 API，Ollama 更方便。

### 5. Ollama 适合什么场景

适合：

- 本地快速体验模型；
- 桌面开发；
- 离线助手；
- 本地 API 服务；
- 不想手动管理 GGUF 和启动参数的用户。

不太适合：

- 大规模生产级并发；
- 需要极致吞吐优化的 GPU 服务；
- 需要精细控制底层推理内核的场景。

## 七、vLLM、llama.cpp、Ollama 对比

| 对比项 | vLLM | llama.cpp | Ollama |
|---|---|---|---|
| 定位 | 高吞吐服务端推理 | 轻量本地推理内核 | 本地模型管理和服务封装 |
| 核心技术 | PagedAttention、continuous batching | GGUF、低比特量化、C/C++ 后端 | 模型管理、Modelfile、API 封装 |
| 主要硬件 | GPU 服务器 | CPU、本地 GPU、Apple Silicon | 本地 CPU/GPU |
| 并发能力 | 强 | 一般 | 一般 |
| 易用性 | 中等 | 中等偏底层 | 高 |
| 适合生产 API | 适合 | 需要额外封装 | 小规模可用 |
| 适合本地离线 | 可以但偏重 | 非常适合 | 非常适合 |
| 模型格式 | Hugging Face 权重等 | GGUF | 通常使用 Ollama 管理的模型/GGUF 生态 |

## 八、常见推理加速技术

### 1. 量化

量化把权重从 FP16/BF16 降到 INT8、INT4 等低精度。

```text
FP16 -> INT8 / INT4
```

优点：

- 显存更低；
- 可以运行更大模型；
- 某些硬件上速度更快。

缺点：

- 可能损失精度；
- 不同量化算法效果差异大；
- 有些硬件对低比特不一定真的更快。

常见方法：

| 方法 | 说明 |
|---|---|
| GPTQ | 后训练量化，常用于 GPU 推理 |
| AWQ | 激活感知权重量化 |
| GGUF quant | llama.cpp 常用量化格式 |
| bitsandbytes | Python 生态中常见 8bit/4bit 方案 |

### 2. FlashAttention

FlashAttention 优化 Attention 计算的显存访问方式。

它不是改变 Attention 数学公式，而是改变计算实现，让 GPU 更高效。

作用：

- 降低显存占用；
- 提高 attention 速度；
- 对长上下文尤其有帮助。

### 3. Continuous Batching

连续批处理用于服务端并发。

它让不同请求可以动态加入或离开 batch，避免 GPU 空转。

vLLM、TGI 等服务框架都重视这类调度。

### 4. Speculative Decoding

投机解码通常使用一个小模型先快速提出多个候选 token，再由大模型验证。

```text
小模型草稿生成多个 token
  -> 大模型验证
  -> 接受一部分 token
```

如果接受率高，可以减少大模型调用次数，提高生成速度。

### 5. Prefix Cache

如果多个请求有相同前缀，例如相同 system prompt：

```text
system prompt 相同
用户问题不同
```

可以缓存相同前缀的 KV，避免重复 prefill。

适合：

- 多轮对话；
- 固定系统提示词；
- RAG 模板固定的服务。

### 6. Tensor Parallel

Tensor Parallel 把单层矩阵计算拆到多张 GPU 上。

适合单张 GPU 放不下或算不动的大模型。

代价是需要 GPU 间通信，部署复杂度更高。

### 7. Pipeline Parallel

Pipeline Parallel 把不同层放到不同 GPU 上。

```text
GPU0: layer 1-10
GPU1: layer 11-20
GPU2: layer 21-30
```

适合超大模型，但会有流水线气泡和调度开销。

## 九、不同场景怎么选

### 1. 本地快速体验

推荐：

```text
Ollama
```

原因：

- 安装和运行简单；
- 自动管理模型；
- 适合命令行和本地 API；
- 不需要理解太多底层细节。

### 2. 本地极简可控部署

推荐：

```text
llama.cpp
```

原因：

- 依赖少；
- 模型格式清晰；
- 参数控制细；
- CPU/GPU/Metal 等后端可选。

### 3. GPU 服务器高并发 API

推荐：

```text
vLLM
```

原因：

- PagedAttention 管理 KV Cache；
- continuous batching 提高吞吐；
- OpenAI-compatible API 方便接入；
- 适合多请求服务。

### 4. NVIDIA 生产级极致优化

可以考虑：

```text
TensorRT-LLM
```

原因：

- 深度优化 NVIDIA GPU；
- 适合对延迟和吞吐要求极高的生产环境；
- 部署复杂度比 Ollama/llama.cpp 更高。

## 十、总结

大模型推理加速的核心不是“换一个工具就一定快”，而是看瓶颈在哪里。

```text
显存不够:
  -> 量化、KV Cache 优化、减小 batch、缩短上下文

并发不够:
  -> vLLM、continuous batching、PagedAttention

本地跑不起来:
  -> llama.cpp、GGUF、低比特量化、Ollama

首 token 慢:
  -> 优化 prefill、prefix cache、缩短 prompt

输出 token 慢:
  -> 优化 decode、量化、GPU kernel、batch 调度
```

三个工具可以这样记：

```text
vLLM:
  面向 GPU 服务端高吞吐，核心是 PagedAttention 和连续批处理。

llama.cpp:
  面向本地轻量推理，核心是 C/C++、GGUF、量化和多硬件后端。

Ollama:
  面向本地易用体验，核心是模型管理、Modelfile 和推理服务封装。
```
