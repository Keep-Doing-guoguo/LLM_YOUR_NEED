# 大模型推理加速面试题 200 道

本文整理大模型推理加速相关面试题与参考答案，覆盖推理流程、性能指标、KV Cache、Batching、Attention 优化、量化、并行部署、推理框架、服务化、多模态推理和线上排障。

## 一、推理基础与性能指标

### 1. 大模型推理和训练的关注点有什么不同？

训练关注 loss、收敛、梯度、数据质量和训练稳定性；推理关注首 token 延迟、输出 token 吞吐、并发能力、显存占用、服务稳定性和部署成本。

### 2. 大模型推理为什么通常比普通模型慢？

因为参数量大、层数深、每生成一个 token 都要经过完整模型，而且自回归生成在 token 维度上天然串行，长上下文还会带来较大的 KV Cache 读写成本。

### 3. 什么是 TTFT？

TTFT 是 Time To First Token，表示从请求进入系统到生成第一个 token 的时间。它主要受 prompt 长度、prefill 计算、排队时间和调度策略影响。

### 4. 什么是 TPOT？

TPOT 是 Time Per Output Token，表示生成阶段每输出一个 token 的平均耗时。它主要反映 decode 阶段效率。

### 5. 什么是 token throughput？

Token throughput 是单位时间内系统处理或生成的 token 数，常见指标包括 input tokens/s、output tokens/s 和 total tokens/s。

### 6. 什么是 request throughput？

Request throughput 是单位时间完成的请求数。它受请求长度分布影响很大，不能单独代表推理系统性能。

### 7. latency 和 throughput 的区别是什么？

Latency 关注单个请求等待多久；throughput 关注系统单位时间处理多少工作。提升吞吐可能通过 batching 增加单请求延迟，因此两者需要权衡。

### 8. 为什么推理性能不能只看 tokens/s？

因为 tokens/s 可能掩盖首 token 延迟、排队时间、长尾延迟、请求失败率和显存利用率。线上服务需要同时看延迟、吞吐、并发和稳定性。

### 9. P50、P95、P99 延迟分别表示什么？

P50 是中位数延迟，P95/P99 表示 95%/99% 请求在该时间内完成。P99 更能反映线上长尾体验和系统抖动。

### 10. 大模型推理的主要瓶颈有哪些？

主要瓶颈包括模型权重读取、KV Cache 显存占用、Attention 计算、decode 串行性、batch 调度、网络传输、采样开销和服务端排队。

## 二、Prefill 与 Decode

### 11. Prefill 阶段是什么？

Prefill 是处理输入 prompt 的阶段，模型一次性计算所有 prompt token 的 hidden states 和 KV Cache，并得到第一个可采样 logits。

### 12. Decode 阶段是什么？

Decode 是逐 token 生成阶段，每一步根据当前上下文和 KV Cache 生成下一个 token，并把新 token 的 K/V 追加到缓存。

### 13. Prefill 和 Decode 的计算特征有什么不同？

Prefill 更像大矩阵批量计算，算力利用率较高；Decode 每步只处理新 token，但要读取大量权重和历史 KV，常受内存带宽限制。

### 14. 为什么长 prompt 会增加首 token 延迟？

因为首 token 之前必须完成整个 prompt 的 prefill，prompt 越长，Attention 和 MLP 计算越多，KV Cache 初始化越大。

### 15. 为什么 decode 阶段通常难以完全并行？

自回归生成要求第 t+1 个 token 依赖第 t 个 token 的结果，因此 token 时间步之间不能完全并行。

### 16. Prefill 阶段 Attention 复杂度是多少？

标准 Attention 在 prompt 长度为 n 时复杂度约为 `O(n^2)`，因为 prompt 内每个 token 都要和其他可见 token 计算注意力。

### 17. Decode 阶段 Attention 每步复杂度是多少？

单步 decode 中，新 token 的 query 需要和历史长度 n 的 key 做 attention，因此每层每步 attention 复杂度约为 `O(n)`。

### 18. 为什么 decode 阶段 batch size 很重要？

单个 token decode 计算粒度小，GPU 利用率容易低。把多个请求合并成 batch 可以提高矩阵计算效率和硬件利用率。

### 19. Prefill 和 decode 可以分离部署吗？

可以。有些系统将 prefill 和 decode 拆到不同 worker 或不同 GPU 池中，针对两阶段不同瓶颈做资源调度。

### 20. Chunked Prefill 是什么？

Chunked Prefill 是把长 prompt 分块处理，使 prefill 不会长时间独占 GPU，便于与 decode 请求混合调度，降低其他请求的等待时间。

## 三、KV Cache

### 21. KV Cache 是什么？

KV Cache 是推理时缓存历史 token 在每层 Attention 中的 Key 和 Value，避免生成每个新 token 时重复计算历史上下文。

### 22. KV Cache 为什么能加速？

历史 token 的 K/V 在生成过程中不变，缓存后每步只计算新增 token 的 K/V，再与历史 K/V 做注意力，减少重复计算。

### 23. KV Cache 主要占用什么资源？

主要占用 GPU 显存。上下文越长、batch 越大、层数越多、KV head 越多，KV Cache 越大。

### 24. KV Cache 大小如何估算？

大致为 `batch * seq_len * num_layers * num_kv_heads * head_dim * 2 * dtype_bytes`，其中 2 表示 K 和 V。

### 25. MHA、MQA、GQA 对 KV Cache 有什么影响？

MHA 每个 attention head 都有独立 KV，缓存最大；MQA 所有 query heads 共享一组 KV，缓存最小；GQA 多个 query heads 共享一组 KV，是折中方案。

### 26. 为什么大模型常用 GQA？

GQA 可以显著减少 KV Cache 和显存带宽压力，同时比 MQA 保留更多表达能力，适合高吞吐推理。

### 27. KV Cache 是否会影响模型输出质量？

正确实现不会改变输出质量。它只是缓存中间结果。如果缓存位置、mask、rope position 或 batch 映射出错，则会导致输出异常。

### 28. KV Cache 和 context length 有什么关系？

KV Cache 与上下文长度近似线性增长。长上下文场景下，即使模型权重能放下，KV Cache 也可能成为显存瓶颈。

### 29. 为什么 KV Cache 会导致并发受限？

每个活跃请求都需要保存自己的上下文 KV。并发越高，总缓存越大，显存耗尽后只能降低并发、缩短上下文或使用更省缓存的模型结构。

### 30. KV Cache 可以量化吗？

可以。KV Cache 量化把 K/V 用低比特存储，降低显存占用和带宽压力，但需要控制精度损失和反量化开销。

## 四、Batching 与调度

### 31. Static Batching 是什么？

Static Batching 是把固定数量请求组成 batch 一起推理。实现简单，但请求长度不一致时容易产生 padding 浪费和等待。

### 32. Dynamic Batching 是什么？

Dynamic Batching 是在短时间窗口内动态收集请求组成 batch，提高吞吐。它需要权衡等待时间和批处理效率。

### 33. Continuous Batching 是什么？

Continuous Batching 是推理过程中动态加入新请求、移除完成请求，每个 decode step 都可重新组织 batch，提高 GPU 利用率。

### 34. Continuous Batching 为什么适合 LLM？

LLM 请求生成长度差异很大，固定 batch 会被短请求或长请求拖累。Continuous Batching 能更细粒度调度活跃序列。

### 35. Batching 会增加延迟吗？

可能会。为了凑 batch，系统可能让请求等待一小段时间。batch 太大也会增加单步计算时间，所以要根据 SLA 调整。

### 36. 为什么 batch 内长度不一致会浪费计算？

传统 batch 需要 padding 到相同长度，短序列的 padding token 也可能占用计算和显存。现代框架会通过更细粒度调度减少浪费。

### 37. Orca 调度思想是什么？

Orca 的核心是 iteration-level scheduling，即以 decode iteration 为粒度调度请求，而不是整条序列固定占用 batch，提高服务端吞吐。

### 38. 请求排队时间为什么重要？

用户感知延迟包含排队和计算。高负载时排队时间可能超过模型计算时间，是 P95/P99 延迟恶化的重要原因。

### 39. 如何降低长尾延迟？

可以限制最大生成长度、区分长短请求队列、使用 chunked prefill、合理 admission control、动态 batch、优先级调度和副本扩容。

### 40. Admission Control 是什么？

Admission Control 是请求准入控制。当系统负载过高或显存不足时，拒绝、排队或降级部分请求，防止整体服务崩溃。

## 五、PagedAttention 与内存管理

### 41. PagedAttention 是什么？

PagedAttention 是 vLLM 中的 KV Cache 管理方式，把每个请求的 KV Cache 拆成固定大小 block，类似操作系统分页管理内存。

### 42. PagedAttention 解决了什么问题？

它减少 KV Cache 的显存碎片和过度预分配，让不同长度请求更灵活地共享显存，提高并发能力。

### 43. 传统 KV Cache 管理有什么问题？

传统方式可能为每个请求预留最大长度缓存，导致大量未使用空间，也容易因请求长度变化造成显存碎片。

### 44. PagedAttention 会提升单请求速度吗？

主要收益是提升多请求并发下的显存利用率和吞吐，不一定显著提升单请求延迟。

### 45. KV block 是什么？

KV block 是固定大小的缓存页，保存一段 token 的 K/V。请求的逻辑序列可映射到多个物理 block。

### 46. 为什么 KV Cache 会有碎片问题？

不同请求长度不同、结束时间不同，如果使用连续内存分配，会产生难以复用的小块空洞，降低可用显存。

### 47. Prefix Caching 是什么？

Prefix Caching 是缓存相同 prompt 前缀的 KV，多个请求共享前缀计算结果，减少重复 prefill。

### 48. Prefix Caching 适合什么场景？

适合系统提示词固定、RAG 模板固定、多轮对话共享历史前缀、批量评测或 agent 工具调用模板重复的场景。

### 49. Prefix Caching 有什么风险？

需要保证 token 序列完全一致、位置编码一致、权限隔离正确。错误共享可能导致上下文污染或隐私泄漏。

### 50. Sliding Window KV Cache 是什么？

Sliding Window KV Cache 只保留最近窗口内的 KV，丢弃更早 token，用于支持窗口注意力模型或降低长对话缓存成本。

## 六、Attention 算子优化

### 51. FlashAttention 是什么？

FlashAttention 是一种 IO-aware attention 算法，通过分块和在线 softmax 减少显存读写，避免显式存储完整 attention 矩阵。

### 52. FlashAttention 为什么快？

它把 Q、K、V 分块放入更快的 SRAM/shared memory 中计算，减少 HBM 往返读写，提升算子效率。

### 53. FlashAttention 是否改变模型结构？

不改变。它是 attention 的高效实现，数学上仍计算标准 scaled dot-product attention。

### 54. FlashAttention 对 prefill 和 decode 哪个更有帮助？

对 prefill 更明显，因为 prefill 需要处理较大的 attention 矩阵。decode 单步 query 很短，瓶颈常在 KV 读取和调度。

### 55. FlashAttention-2 改进了什么？

FlashAttention-2 进一步优化并行划分和 GPU 利用率，减少非矩阵乘法操作开销，通常比第一版更快。

### 56. FlashDecoding 是什么？

FlashDecoding 是面向 decode 阶段的 attention 优化，通过并行化长 KV 读取和规约来加速单步生成，适合长上下文推理。

### 57. 什么是 fused kernel？

Fused kernel 是把多个小算子合并成一个 GPU kernel，减少 kernel launch 开销和中间结果读写。

### 58. 推理中常见可融合的算子有哪些？

常见包括 bias+activation、RMSNorm、RoPE、QKV projection、attention softmax、MLP 中的门控激活、残差加法等。

### 59. 为什么小算子会拖慢推理？

小算子计算量少但 kernel launch 和显存读写开销固定，频繁调用会导致 GPU 利用率低。

### 60. RoPE 算子为什么也需要优化？

RoPE 每层每步都要作用在 Q/K 上。虽然计算不大，但在 decode 高频小 batch 场景中也可能成为可见开销。

## 七、矩阵乘与硬件利用

### 61. GEMM 是什么？

GEMM 是通用矩阵乘法，是 Transformer 中线性层和部分 attention 计算的核心算子。

### 62. 为什么大模型推理依赖高效 GEMM？

Transformer 的 QKV 投影、输出投影和 MLP 都是大矩阵乘法。GEMM 效率直接决定算力利用率。

### 63. Tensor Core 是什么？

Tensor Core 是 NVIDIA GPU 中专门加速矩阵乘加的硬件单元，支持 FP16、BF16、INT8、FP8 等精度。

### 64. 为什么 shape 会影响推理速度？

矩阵维度是否对齐硬件 tile、batch 是否足够大、hidden size 是否适配 Tensor Core，都会影响 kernel 效率。

### 65. 为什么 decode 单 batch 容易 GPU 利用率低？

每步只处理一个 token，矩阵乘的 batch 维度小，计算粒度不足，无法充分填满 GPU。

### 66. 如何提升 decode 阶段 GPU 利用率？

常见方法是 continuous batching、增大并发、合并请求、使用 speculative decoding、优化 KV 读取和使用高效 kernel。

### 67. 什么是 memory-bound？

memory-bound 指性能瓶颈主要在内存读写带宽，而不是算力。decode 阶段经常需要读取大量权重和 KV，因此容易 memory-bound。

### 68. 什么是 compute-bound？

compute-bound 指瓶颈主要在计算能力。长 prompt prefill 大矩阵乘较多，更可能接近 compute-bound。

### 69. Roofline 模型有什么用？

Roofline 模型用计算强度和硬件峰值来判断程序受算力还是带宽限制，帮助定位优化方向。

### 70. 为什么 FP16/BF16 比 FP32 推理快？

低精度数据更小，显存带宽压力更低，并能使用 Tensor Core 加速矩阵乘，因此通常速度更快、显存更省。

## 八、量化基础

### 71. 推理量化是什么？

推理量化是用低比特数表示权重、激活或 KV Cache，以降低显存占用、带宽压力和计算成本。

### 72. 常见量化精度有哪些？

常见有 FP16、BF16、FP8、INT8、INT4、NF4、GPTQ/AWQ 的 4-bit 权重量化，以及 KV Cache 的 INT8/FP8 量化。

### 73. Weight-only Quantization 是什么？

Weight-only Quantization 只量化模型权重，激活通常仍用 FP16/BF16。它部署相对简单，常用于大模型推理。

### 74. Weight-Activation Quantization 是什么？

它同时量化权重和激活，可能获得更高推理加速，但校准和精度保持更难。

### 75. 对称量化和非对称量化有什么区别？

对称量化用 0 作为中心，通常只有 scale；非对称量化有 scale 和 zero point，能更好表示偏移分布但实现更复杂。

### 76. Per-tensor 和 per-channel 量化区别是什么？

Per-tensor 整个张量共享一个 scale，简单但精度较差；per-channel 每个通道独立 scale，精度更好但元数据和实现更复杂。

### 77. Group-wise 量化是什么？

Group-wise 量化把权重按小组分块，每组一个 scale，常用于 4-bit 权重量化，在压缩率和精度之间折中。

### 78. 量化为什么可能降低模型效果？

低比特表示会引入舍入误差，破坏权重、激活或 attention 分布，尤其对异常值、长上下文和复杂推理任务更敏感。

### 79. 量化一定能加速吗？

不一定。若硬件或 kernel 不支持低比特高效计算，反量化开销可能抵消收益。量化至少通常能省显存。

### 80. 量化校准是什么？

校准是用一批代表性数据统计激活范围或优化量化参数，使量化模型尽量贴近原模型输出。

## 九、主流量化方法

### 81. GPTQ 是什么？

GPTQ 是一种训练后权重量化方法，利用近似二阶信息逐层量化权重，尽量降低量化误差。

### 82. AWQ 是什么？

AWQ 是 Activation-aware Weight Quantization，根据激活重要性保护关键权重通道，常用于 4-bit 推理部署。

### 83. SmoothQuant 是什么？

SmoothQuant 把激活中的异常值平滑转移到权重中，使权重和激活都更容易 INT8 量化。

### 84. NF4 是什么？

NF4 是 NormalFloat4，一种面向近似正态分布权重的 4-bit 数据格式，常见于 QLoRA 训练。

### 85. FP8 推理有什么特点？

FP8 比 FP16 更省显存和带宽，并能利用新硬件加速，但需要硬件、kernel 和数值策略支持。

### 86. INT8 和 INT4 推理区别是什么？

INT8 精度损失通常更小、硬件支持更成熟；INT4 压缩率更高，但更依赖量化算法和 kernel，精度风险更大。

### 87. KV Cache 量化和权重量化有什么区别？

权重量化压缩固定模型参数；KV Cache 量化压缩每个请求动态产生的缓存，主要影响长上下文和高并发显存。

### 88. 量化后为什么还需要反量化？

很多计算仍在 FP16/BF16 中执行，低比特权重需要反量化成计算格式参与矩阵乘，或者在专用 kernel 中边反量化边计算。

### 89. 量化模型如何评估？

应比较困惑度、任务指标、长上下文表现、代码/数学能力、对话质量、吞吐、显存和稳定性，而不只看单条样例。

### 90. 为什么数学和代码任务对量化更敏感？

这类任务需要精确 token 分布和多步推理，量化误差可能在生成过程中累积，导致中间步骤或符号细节错误。

## 十、Speculative Decoding

### 91. Speculative Decoding 是什么？

Speculative Decoding 使用小模型先草拟多个 token，再由大模型并行验证，从而减少大模型串行 decode 次数。

### 92. Speculative Decoding 为什么能加速？

如果小模型草拟 token 被大模型接受，大模型一次 forward 可确认多个 token，相当于减少逐 token 调用次数。

### 93. Draft model 是什么？

Draft model 是负责快速生成候选 token 的小模型。它需要速度快，并且输出分布尽量接近目标大模型。

### 94. Target model 是什么？

Target model 是最终保证输出分布正确的大模型。它会验证 draft tokens 是否可以接受。

### 95. Speculative Decoding 的加速取决于什么？

取决于 draft 模型速度、候选 token 接受率、验证批量大小、目标模型大小和系统实现开销。

### 96. Draft 模型越小越好吗？

不一定。太小虽然快，但接受率低；太大接受率高但草拟成本高。需要找到速度和分布接近度的平衡。

### 97. Speculative Decoding 会改变输出分布吗？

严格实现下不会改变目标模型采样分布。它只是用接受-拒绝机制加速采样。

### 98. Medusa 是什么？

Medusa 是一种多 token 预测加速方法，在模型上增加多个预测头，一次预测多个后续 token，再进行验证。

### 99. EAGLE 是什么？

EAGLE 是一种基于特征层预测未来 token 表示的推测解码方法，目标是在较高接受率下提升生成速度。

### 100. Speculative Decoding 适合所有场景吗？

不适合。低并发、短输出、draft 接受率低或系统已被其他瓶颈限制时，加速收益可能不明显。

## 十一、并行推理

### 101. Tensor Parallel 推理是什么？

Tensor Parallel 把单层矩阵计算切到多张 GPU 上，例如切分 attention head 或 MLP 线性层，用于部署单卡放不下或需要更高吞吐的模型。

### 102. Pipeline Parallel 推理是什么？

Pipeline Parallel 把模型不同层放到不同 GPU，上游 GPU 处理前几层，下游 GPU 处理后几层。它适合模型太大单卡放不下的情况。

### 103. Data Parallel 推理是什么？

Data Parallel 推理是在多张 GPU 上各放一份完整模型，不同请求分配到不同副本，适合提高整体服务吞吐。

### 104. Expert Parallel 是什么？

Expert Parallel 用于 MoE 模型，把不同专家分布到不同设备上。token 根据路由发送到对应专家计算。

### 105. Tensor Parallel 的代价是什么？

它需要 GPU 间通信，例如 all-reduce 或 all-gather。通信开销可能抵消多卡计算收益。

### 106. Pipeline Parallel 的代价是什么？

它可能产生 pipeline bubble，并增加跨设备传输延迟。decode 阶段 token 串行，流水线效率可能受限。

### 107. 推理中什么时候优先用 Data Parallel？

如果单卡能放下模型，并且请求量较大，Data Parallel 简单高效，通常优先用于水平扩容。

### 108. 推理中什么时候需要 Tensor Parallel？

当模型权重单卡放不下，或单卡延迟/吞吐无法满足需求时，可以使用 Tensor Parallel。

### 109. 多机推理有什么额外问题？

多机通信延迟更高，网络带宽更容易成为瓶颈，还涉及节点故障、调度、拓扑感知和部署复杂度。

### 110. NVLink 和 PCIe 对推理有什么影响？

NVLink 带宽和延迟通常优于 PCIe，多 GPU 张量并行或专家并行通信更快。PCIe 环境下跨卡通信可能成为瓶颈。

## 十二、推理框架

### 111. vLLM 的核心优势是什么？

vLLM 的核心优势是 PagedAttention、continuous batching、高效 KV Cache 管理和 OpenAI 兼容服务接口，适合高吞吐在线推理。

### 112. TensorRT-LLM 的核心优势是什么？

TensorRT-LLM 针对 NVIDIA GPU 做深度算子优化、图优化、量化和并行支持，适合追求极致性能的生产部署。

### 113. llama.cpp 的核心优势是什么？

llama.cpp 轻量、易部署，支持 CPU 和多种本地硬件后端，GGUF 格式和低比特量化生态成熟，适合本地推理。

### 114. Ollama 的定位是什么？

Ollama 更像本地模型管理和运行封装，简化模型下载、启动和 API 使用，底层常依赖 llama.cpp 类能力。

### 115. Hugging Face TGI 是什么？

TGI 是 Hugging Face 的 Text Generation Inference 服务框架，支持流式输出、batching、张量并行和生产服务能力。

### 116. DeepSpeed-Inference 适合什么场景？

适合已有 DeepSpeed 生态、需要模型并行、kernel injection 或和训练部署链路结合的场景。

### 117. SGLang 是什么？

SGLang 是面向结构化生成和 LLM 服务的推理框架，强调高效 runtime、前缀复用、复杂 prompting 和 agent 场景调度。

### 118. LMDeploy 是什么？

LMDeploy 是大模型压缩和部署工具，支持 TurboMind、量化和服务化，常见于 InternLM 等生态。

### 119. 选择推理框架时看哪些因素？

看模型支持、硬件支持、吞吐延迟、量化能力、并行能力、API 兼容性、社区成熟度、运维便利性和业务场景。

### 120. 为什么同一个模型不同框架速度差异很大？

差异来自 kernel 实现、batch 调度、KV Cache 管理、量化格式、图优化、并行策略和服务端开销。

## 十三、模型格式与部署

### 121. safetensors 是什么？

safetensors 是一种安全、快速的模型权重格式，避免 pickle 反序列化风险，并支持高效加载。

### 122. GGUF 是什么？

GGUF 是 llama.cpp 生态常用模型格式，支持保存模型结构元信息和量化权重，适合本地推理。

### 123. ONNX 在推理中有什么作用？

ONNX 是跨框架模型交换格式，可用于导出模型并接入 ONNX Runtime、TensorRT 等推理后端。

### 124. TensorRT engine 是什么？

TensorRT engine 是 TensorRT 根据模型和目标硬件编译优化后的执行计划，包含图优化、kernel 选择和精度策略。

### 125. 静态 shape 和动态 shape 有什么区别？

静态 shape 固定输入尺寸，优化更充分；动态 shape 支持变长输入，更灵活但优化和内存规划更复杂。

### 126. 为什么 LLM 部署常需要 trust_remote_code？

一些模型自定义了结构、RoPE、attention 或 generation 逻辑，需要加载仓库中的自定义代码。但生产环境要审查安全风险。

### 127. tokenizer 部署不一致会怎样？

如果 tokenizer 与模型训练时不一致，输入 token id 会错，轻则效果下降，重则输出乱码或完全不可用。

### 128. chat template 有什么作用？

chat template 把多轮对话转换成模型预训练或指令微调时熟悉的文本格式。模板不匹配会显著影响回答质量。

### 129. 模型权重加载慢怎么优化？

可以使用 safetensors、并行加载、本地 SSD、权重分片、常驻服务、镜像预热和避免频繁冷启动。

### 130. 冷启动是什么？

冷启动是服务首次加载模型、初始化 kernel、分配显存和编译图的过程，通常延迟较高。

## 十四、服务化与流式输出

### 131. 流式输出为什么重要？

流式输出可以在完整回答生成前先返回 token，显著改善用户感知延迟，尤其适合长回答。

### 132. SSE 在 LLM 服务中有什么作用？

SSE 是 Server-Sent Events，常用于服务端向客户端持续推送生成 token，实现简单的流式响应。

### 133. WebSocket 和 SSE 有什么区别？

WebSocket 是双向通信，适合交互复杂场景；SSE 是服务端单向推送，适合文本流式输出，部署更简单。

### 134. OpenAI-compatible API 有什么价值？

它让推理服务兼容 OpenAI SDK 和生态工具，降低业务接入成本，也便于替换底层模型或框架。

### 135. 线上推理服务为什么要限流？

限流可以防止流量突增压垮 GPU 服务，保护 P99 延迟和系统稳定性。

### 136. 最大输入长度和最大输出长度为什么要限制？

长度直接影响 prefill 成本、KV Cache 和服务时间。限制长度可以控制成本、防止滥用并降低长尾延迟。

### 137. 多租户推理有什么风险？

风险包括资源争抢、上下文隔离错误、缓存泄漏、优先级不公平和单租户流量冲击整体服务。

### 138. 如何做服务降级？

可以切小模型、降低最大输出长度、关闭长上下文、降低采样复杂度、排队或拒绝低优先级请求。

### 139. 为什么要做健康检查？

健康检查用于发现模型服务进程异常、GPU OOM、响应阻塞或依赖故障，便于负载均衡及时摘除坏实例。

### 140. 推理服务常见超时设置有哪些？

包括排队超时、首 token 超时、整体请求超时、空闲连接超时和上游网关超时。

## 十五、采样与生成控制

### 141. 采样会影响推理速度吗？

会，但通常不是最大瓶颈。复杂约束解码、大词表排序、beam search 或 grammar decoding 会增加额外开销。

### 142. Greedy decoding 为什么最快？

它每步只取最大 logits 对应 token，不需要随机采样或维护多个候选路径，计算和实现最简单。

### 143. Beam search 为什么慢？

Beam search 每步维护多个候选序列，相当于扩大有效 batch，并需要排序和得分管理，因此计算和显存开销更大。

### 144. Top-k 和 Top-p 哪个更耗时？

都需要对 logits 做筛选。Top-k 通常可用 topk 算子；Top-p 往往涉及排序或累积概率，开销可能更高。

### 145. Temperature 对速度有影响吗？

单独 temperature 缩放开销很小，主要影响输出分布和生成长度，而不是单步计算速度。

### 146. Grammar constrained decoding 是什么？

它通过语法或状态机限制模型只能生成合法 token，适合 JSON、SQL、代码片段等结构化输出，但会增加 logits 过滤开销。

### 147. JSON mode 为什么可能变慢？

因为每步要根据当前状态约束合法 token 集合，复杂实现可能增加 CPU 或 GPU 侧后处理开销。

### 148. 生成长度为什么影响成本？

每多生成一个 token 都要执行一次 decode，经过所有模型层，并追加 KV Cache。因此输出长度通常与服务成本近似线性相关。

### 149. stop sequence 匹配有什么性能影响？

通常影响较小，但如果 stop sequence 多、匹配逻辑复杂或在高并发 CPU 侧处理，也可能成为服务开销。

### 150. 为什么低温度可能减少平均延迟？

低温度输出更确定，可能更早生成 EOS 或较少发散，但这不是稳定保证，实际取决于任务和停止条件。

## 十六、长上下文推理

### 151. 长上下文推理为什么贵？

长上下文会增加 prefill attention 计算、KV Cache 显存和 decode 阶段每步读取的历史 KV 长度。

### 152. 长上下文的主要优化方向有哪些？

包括 RoPE scaling、稀疏或窗口注意力、KV Cache 压缩、分块 prefill、检索式上下文压缩、prefix caching 和更高效 attention kernel。

### 153. Sliding Window Attention 对推理有什么好处？

它限制每个 token 关注固定窗口，降低长序列 attention 和 KV 读取成本，适合局部依赖较强的任务。

### 154. 上下文压缩是什么？

上下文压缩是在送入模型前或生成中将长历史总结、筛选或压缩，减少 token 数，从源头降低推理成本。

### 155. RAG 能降低推理成本吗？

可以。RAG 通过检索相关片段替代塞入全部文档，减少无关上下文。但检索系统本身也有额外延迟和成本。

### 156. Prefix caching 对长上下文有什么帮助？

如果很多请求共享长系统提示词、文档前缀或对话历史，prefix caching 可以复用已计算 KV，降低 TTFT。

### 157. 为什么长上下文会影响 decode 速度？

每个新 token 的 query 都要访问更长历史 KV，读取和 attention 计算随上下文长度增长。

### 158. Long context benchmark 为什么不能只看最大长度？

最大长度只说明能处理，不说明能准确使用。还要看检索、推理、抗干扰能力和不同位置的稳定性。

### 159. RoPE scaling 是否属于推理加速？

它主要扩展上下文能力，不直接加速；但如果能减少截断、重跑或复杂分块策略，间接改善系统效率。

### 160. 长对话服务如何控制 KV Cache 膨胀？

可以限制历史轮数、总结旧上下文、滑窗保留、RAG 化记忆、KV 压缩、降低并发或使用更省 KV 的模型。

## 十七、多模态推理加速

### 161. 多模态推理为什么比纯文本更贵？

图像、视频会转换成视觉 token，占用上下文窗口，增加 prefill 计算和 KV Cache。视觉编码器本身也有额外计算。

### 162. 视觉 token 数量由什么决定？

通常由图像分辨率、patch size、视觉编码器结构、动态分辨率策略和 resampler/query 数量决定。

### 163. 降低视觉 token 的方法有哪些？

可以降低输入分辨率、使用 resampler、Q-Former、token pruning、区域裁剪、图像压缩或只保留关键帧。

### 164. 视频大模型推理的主要瓶颈是什么？

主要瓶颈是帧数多导致视觉 token 爆炸、视觉编码器计算重、prefill 长、KV Cache 大，以及跨帧信息建模成本高。

### 165. 动态分辨率有什么利弊？

动态分辨率能保留细节、提升 OCR 和定位能力，但会增加视觉 token 数量，推理成本和延迟更高。

### 166. 多图输入为什么容易慢？

每张图都会产生视觉 token，多图输入等价于显著增加 prompt 长度，从而增加 prefill 和 KV Cache。

### 167. 多模态模型可以做视觉 KV Cache 复用吗？

可以。如果同一图像在多轮对话中重复使用，视觉 token 对应的 KV 可复用，但需要框架支持和严格上下文一致性。

### 168. OCR 类任务为什么对分辨率敏感？

文字细节依赖像素分辨率，过度压缩会丢失字符信息。降低 token 成本和保留文字细节之间需要权衡。

### 169. 多模态服务如何做降级？

可以限制图片数量、降低分辨率、减少视频帧、切换小视觉编码器、关闭高精度 OCR 模式或转纯文本摘要。

### 170. 多模态推理如何评估性能？

需要分别统计视觉编码耗时、LLM prefill、decode、视觉 token 数、显存、TTFT 和端到端延迟。

## 十八、CPU、本地与边缘推理

### 171. CPU 推理为什么慢？

CPU 的矩阵乘吞吐和内存带宽通常远低于 GPU，尤其大模型层数深、参数多，逐 token 生成会很慢。

### 172. CPU 推理如何优化？

可以使用低比特量化、线程并行、NUMA 绑定、BLAS/oneDNN、KV Cache 优化、减少上下文和选择小模型。

### 173. llama.cpp 为什么适合本地推理？

它轻量、依赖少、支持多种量化格式和硬件后端，能在 CPU、Metal、CUDA 等环境运行。

### 174. Metal 推理是什么？

Metal 是 Apple 平台的 GPU 计算接口，llama.cpp 等框架可利用 Apple Silicon GPU 加速本地推理。

### 175. 边缘设备推理的关键限制是什么？

关键限制是内存、算力、功耗、散热和模型体积。因此常使用小模型、量化、蒸馏和任务专用优化。

### 176. 端侧推理为什么重视模型大小？

端侧内存有限，模型越大加载越慢、耗电越高、响应越慢。小模型能提供更好的交互体验。

### 177. NPU 推理有什么特点？

NPU 针对矩阵计算和低精度运算优化，能效较好，但通常对模型结构、算子和量化格式支持有限。

### 178. 本地推理和云端推理如何取舍？

本地隐私好、延迟稳定、无网络依赖，但算力有限；云端模型更强、吞吐更高，但有成本、网络和隐私问题。

### 179. 小模型蒸馏对推理有什么价值？

蒸馏能把大模型能力迁移到小模型，降低延迟和成本，适合固定任务或高频场景。

### 180. 端侧长上下文为什么更困难？

长上下文需要大量内存保存 KV Cache，而端侧内存和带宽有限，因此很容易出现速度慢或内存不足。

## 十九、线上监控与排障

### 181. 推理服务需要监控哪些指标？

需要监控 QPS、TTFT、TPOT、P50/P95/P99、GPU 利用率、显存、KV Cache 使用率、队列长度、失败率和 OOM 次数。

### 182. GPU 利用率高是否一定好？

不一定。GPU 高利用率可能代表吞吐好，也可能代表过载导致排队和长尾延迟升高，需要结合延迟和队列看。

### 183. 显存没满但吞吐低可能是什么原因？

可能是 batch 太小、decode 串行导致 GPU 利用率低、CPU 调度瓶颈、kernel 不高效、网络慢或采样后处理开销大。

### 184. 显存 OOM 常见原因有哪些？

常见原因是并发过高、上下文过长、max tokens 设置过大、KV Cache 预分配过大、模型副本过多或显存碎片。

### 185. 首 token 延迟突然升高怎么排查？

看排队时间、prompt 长度分布、prefill batch、prefix cache 命中率、GPU 利用率、上游网络和是否发生冷启动。

### 186. 输出速度突然变慢怎么排查？

看 decode batch 大小、上下文长度、KV Cache 读写、GPU 带宽、采样参数、是否混入超长请求和是否发生降频。

### 187. 模型输出乱码可能和推理部署什么有关？

可能是 tokenizer 不匹配、chat template 错误、权重格式转换错误、量化损坏、特殊 token 配置错误或精度溢出。

### 188. 为什么压测要使用真实长度分布？

LLM 性能高度依赖输入和输出长度。只用固定短 prompt 压测会严重高估线上吞吐和低估长尾延迟。

### 189. 压测时应记录哪些长度信息？

应记录 prompt token 数、生成 token 数、总 token 数、并发数、请求到达分布和不同长度区间的延迟。

### 190. 如何判断系统需要扩容？

当 QPS 增长导致排队时间、P95/P99、失败率或 OOM 明显上升，且优化已接近瓶颈时，需要增加副本或更强硬件。

## 二十、综合设计与面试深挖

### 191. 如果让你优化一个 LLM 推理服务，你会先看什么？

先看业务目标和瓶颈：TTFT、TPOT、QPS、上下文长度、输出长度、并发、显存和成本。然后通过监控和压测判断是 prefill、decode、KV、调度还是网络瓶颈。

### 192. 如何降低 TTFT？

可减少 prompt token、启用 prefix caching、优化 prefill kernel、使用 chunked prefill、减少排队、预热模型、选择更小模型或分离 prefill/decode。

### 193. 如何提升 decode 吞吐？

可使用 continuous batching、GQA/MQA、KV Cache 优化、speculative decoding、高效 kernel、量化、增大并发和合理设置 max tokens。

### 194. 如何降低推理显存？

可使用权重量化、KV Cache 量化、GQA/MQA、小模型、限制上下文和输出长度、PagedAttention、CPU offload 或模型并行。

### 195. 如何在质量和速度之间做权衡？

可以选择模型大小、量化精度、上下文长度、采样策略、RAG 压缩和并发策略。关键是用业务评测集验证质量损失是否可接受。

### 196. 为什么不能盲目上最大模型？

最大模型成本高、延迟高、并发低，不一定适合所有任务。很多固定场景用小模型、蒸馏模型或路由策略更划算。

### 197. 什么是模型路由？

模型路由是根据请求难度、用户等级、任务类型或成本预算选择不同模型，例如简单问题走小模型，复杂问题走大模型。

### 198. 推理加速中最容易被忽略的问题是什么？

最容易忽略真实请求长度分布、排队时间、chat template/tokenizer 一致性、KV Cache 显存、长尾延迟和线上失败恢复。

### 199. 如何设计一次可靠的推理加速实验？

固定模型、数据集、硬件、并发、输入输出长度和采样参数，分别记录延迟、吞吐、显存、质量指标，并与 baseline 对比。

### 200. 推理加速的核心主线是什么？

核心主线是减少重复计算、提高 GPU 利用率、降低显存和带宽压力、优化调度、控制生成长度，并在质量、延迟、吞吐和成本之间做工程权衡。
