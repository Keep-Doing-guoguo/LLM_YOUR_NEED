# 大模型推理阶段与名词说明

大模型推理指的是：模型已经训练好，不再更新参数，用户输入 prompt 后，模型根据已有权重生成回答。

训练阶段关注的是：

```text
输入样本 -> 前向计算 -> 计算 loss -> 反向传播 -> 更新参数
```

推理阶段关注的是：

```text
输入 prompt -> 前向计算 -> 采样 token -> 拼接到上下文 -> 继续生成
```

## 一、推理整体流程

以 Decoder-only 大模型为例：

```text
用户输入文本
  -> Tokenizer 编码成 input_ids
  -> Prefill 阶段处理整段 prompt
  -> 得到 KV Cache
  -> Decode 阶段逐 token 生成
  -> 采样策略选择下一个 token
  -> Tokenizer 解码成文本
```

完整链路：

```text
Prompt
  -> input_ids
  -> model forward
  -> logits
  -> sampling / search
  -> next_token
  -> append
  -> repeat
```

## 二、Prefill 阶段

Prefill 是推理的第一阶段。模型一次性处理用户输入的所有 prompt token。

例如 prompt：

```text
请解释 Transformer 的 Attention 机制
```

分词后有 20 个 token，Prefill 阶段会把这 20 个 token 一次送进模型。

Prefill 的主要任务：

- 计算 prompt 中每个 token 的 hidden state；
- 为每一层 Attention 生成历史 K/V；
- 建立 KV Cache；
- 输出最后一个位置的 logits，用于生成第一个新 token。

特点：

| 特点 | 说明 |
|---|---|
| 计算密集 | prompt 越长，计算越多 |
| 可以并行 | prompt 内所有 token 可以并行处理 |
| 产生 KV Cache | 后续 decode 会复用 |

## 三、Decode 阶段

Decode 是逐 token 生成阶段。

```text
第 1 步: 根据 prompt 生成 token1
第 2 步: 根据 prompt + token1 生成 token2
第 3 步: 根据 prompt + token1 + token2 生成 token3
```

Decode 阶段每次只输入最新生成的 token，但会读取之前缓存的 KV。

```text
当前 token
  -> 计算当前 Q/K/V
  -> 当前 Q 与历史 K 做 attention
  -> 输出 logits
  -> 采样 next token
```

特点：

| 特点 | 说明 |
|---|---|
| 串行生成 | 下一个 token 依赖上一个 token |
| 对延迟敏感 | 每步都要尽快输出 |
| 依赖 KV Cache | 避免重复计算历史上下文 |

## 四、KV Cache

KV Cache 是推理中最重要的优化之一。

在 Attention 中，每个 token 都会产生 K 和 V：

```text
K: Key
V: Value
```

生成第 n 个 token 时，模型需要关注前面所有 token。如果没有 KV Cache，每一步都要重新计算历史 token 的 K/V。

有了 KV Cache：

```text
历史 K/V 已保存
当前只计算新 token 的 K/V
然后把新 K/V 追加到 cache
```

KV Cache 的显存占用和这些因素有关：

```text
层数
batch size
上下文长度
hidden size
KV heads 数量
数据类型
```

上下文越长，KV Cache 越大。

## 五、Logits

模型最后输出的是 logits。

```text
logits: [batch, vocab_size]
```

logits 是每个 token 的原始分数，还不是概率。

例如：

```text
"北京" -> 5.2
"上海" -> 4.7
"苹果" -> -1.3
```

经过 softmax 后才变成概率。

```text
prob = softmax(logits)
```

## 六、Temperature

temperature 控制生成的随机性。

```text
adjusted_logits = logits / temperature
```

| temperature | 效果 |
|---|---|
| 低，例如 0.1、0.3 | 更确定，更保守 |
| 中，例如 0.7、0.8 | 平衡稳定和多样性 |
| 高，例如 1.2、1.5 | 更随机，更发散 |

如果 temperature 很低，模型倾向于选择最高概率 token。

如果 temperature 很高，低概率 token 也更容易被采到。

## 七、Top-k

Top-k 表示只从概率最高的 k 个 token 中采样。

```text
top_k = 50
```

流程：

```text
所有 token 概率
  -> 只保留前 50 个
  -> 重新归一化
  -> 采样
```

作用：

- 避免采到极低概率的奇怪 token；
- 控制生成范围；
- 提高输出稳定性。

## 八、Top-p / Nucleus Sampling

Top-p 不是固定保留 k 个 token，而是保留累计概率达到 p 的最小 token 集合。

```text
top_p = 0.9
```

例如 token 概率排序：

```text
A: 0.40
B: 0.25
C: 0.15
D: 0.08
E: 0.04
...
```

如果 top_p = 0.8，则保留：

```text
A + B + C = 0.80
```

Top-p 比 Top-k 更动态，适合开放式生成。

## 九、Greedy Search

Greedy Search 每一步都选概率最大的 token。

```text
next_token = argmax(logits)
```

优点：

- 稳定；
- 快；
- 可复现。

缺点：

- 容易死板；
- 可能陷入重复；
- 对开放写作不够自然。

适合：

- 确定性问答；
- 代码补全；
- 格式化输出。

## 十、Beam Search

Beam Search 会同时保留多个候选序列。

```text
beam_size = 4
```

每一步扩展多个候选，然后保留总分最高的 beam。

适合：

- 翻译；
- 摘要；
- 需要较稳定序列的任务。

但在大语言模型对话中，Beam Search 有时会导致回答过于模板化。

## 十一、Repetition Penalty

重复惩罚用于降低模型反复生成同一段内容的概率。

```text
repetition_penalty = 1.1
```

如果某个 token 已经出现过，就降低它再次被选中的概率。

适合处理：

- 重复句子；
- 循环输出；
- 某些 token 不断出现。

## 十二、Max New Tokens 和 Context Length

### 1. max_new_tokens

最多生成多少新 token。

```text
max_new_tokens = 512
```

它不包括 prompt token。

### 2. max_length

有些框架中的 max_length 表示：

```text
prompt tokens + generated tokens 的总长度
```

容易和 max_new_tokens 混淆。

### 3. context length

模型最多能处理的上下文长度。

```text
context_length = prompt_tokens + generated_tokens
```

如果超过模型限制，需要截断、滑动窗口或使用长上下文模型。

## 十三、Batch、吞吐和延迟

### 1. Latency

延迟表示用户发出请求到收到结果需要多久。

常见指标：

| 指标 | 说明 |
|---|---|
| TTFT | Time To First Token，首 token 延迟 |
| TPOT | Time Per Output Token，每个输出 token 耗时 |
| E2E Latency | 端到端总延迟 |

### 2. Throughput

吞吐表示单位时间能处理多少 token 或请求。

常见指标：

```text
tokens/s
requests/s
```

提高 batch size 通常能提高吞吐，但可能增加单个请求延迟。

### 3. Continuous Batching

连续批处理会动态把不同时间来的请求合并执行。

```text
请求 A 正在 decode
请求 B 新到达
请求 C 新到达
调度器把它们组合成动态 batch
```

这类机制常见于 vLLM、TGI 等推理框架。

## 十四、PagedAttention

PagedAttention 是 vLLM 中的关键思想之一，用类似操作系统分页的方式管理 KV Cache。

普通 KV Cache 如果连续分配，容易浪费显存。

PagedAttention 把 KV Cache 分成 block：

```text
Request A -> block 1, block 5, block 9
Request B -> block 2, block 3
```

优点：

- 降低 KV Cache 显存碎片；
- 支持更高并发；
- 更适合动态 batch。

## 十五、量化推理

推理时常用量化降低显存和提高速度。

常见格式：

| 格式 | 说明 |
|---|---|
| FP16 / BF16 | 半精度，常规部署 |
| INT8 | 8bit 量化，精度损失较小 |
| INT4 | 4bit 量化，显存更低 |
| GPTQ | 常见权重量化方法 |
| AWQ | 激活感知权重量化 |
| GGUF | llama.cpp 常见格式 |

量化优点：

- 显存占用低；
- 可部署更大模型；
- 有时推理更快。

缺点：

- 可能有精度损失；
- 某些硬件或框架不一定加速；
- 长文本和复杂推理可能更敏感。

## 十六、常见推理参数组合

### 1. 稳定问答

```text
temperature = 0.2
top_p = 0.8
top_k = 20
max_new_tokens = 512
```

### 2. 创意写作

```text
temperature = 0.8
top_p = 0.95
top_k = 50
max_new_tokens = 1024
```

### 3. 代码生成

```text
temperature = 0.1
top_p = 0.9
max_new_tokens = 1024
```

### 4. JSON / 结构化输出

```text
temperature = 0.0 或 0.1
top_p = 1.0
max_new_tokens = 根据结构长度设置
```

如果框架支持，结构化输出最好配合 grammar、json schema 或 constrained decoding。

## 十七、推理阶段名词表

| 名词 | 说明 |
|---|---|
| Prompt | 用户输入给模型的文本 |
| Token | 模型处理文本的最小单位 |
| Tokenizer | 文本和 token id 之间的转换器 |
| Prefill | 一次处理完整 prompt 的阶段 |
| Decode | 逐 token 生成的阶段 |
| Logits | 模型输出的词表原始分数 |
| Softmax | 把 logits 转成概率 |
| Sampling | 根据概率选择下一个 token |
| Greedy | 每次选概率最高 token |
| Beam Search | 保留多个候选序列 |
| Temperature | 控制随机性 |
| Top-k | 只从前 k 个 token 采样 |
| Top-p | 从累计概率达到 p 的 token 集合采样 |
| KV Cache | 缓存历史 token 的 Key/Value |
| Context Length | 模型可处理的总 token 长度 |
| max_new_tokens | 最多生成的新 token 数 |
| TTFT | 首 token 延迟 |
| Throughput | 吞吐量 |
| Quantization | 量化，降低权重精度 |
| Continuous Batching | 动态批处理多个请求 |

## 十八、总结

大模型推理可以拆成两段：

```text
Prefill: 处理 prompt，建立 KV Cache
Decode: 逐 token 生成，复用 KV Cache
```

推理效果主要受这些参数影响：

```text
temperature
top_k
top_p
max_new_tokens
repetition_penalty
context_length
```

推理性能主要受这些因素影响：

```text
模型大小
上下文长度
KV Cache
batch size
量化方式
推理框架
GPU 显存和带宽
```
